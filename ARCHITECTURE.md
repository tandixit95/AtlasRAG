# AtlasRAG Architecture

## Design goal

AtlasRAG is a small, auditable retrieval core for controlled public experiments. Its first responsibility is correctness: provenance must survive every stage, authorization must fail closed, score semantics must stay honest, and behavior must be deterministic enough for regression testing.

It is not presented as a distributed production search service.

## Domain and ingestion boundary

```text
external source
     |
     v
DocumentSource.load()
     |
     v
  Document
  - document_id: logical source identity
  - source_uri: provenance anchor
  - text: exact ingested payload
  - content_sha256: source-version fingerprint
  - metadata: immutable source and access metadata
     |
     v
ChunkingStrategy.chunk()
     |
     v
   Chunk
  - chunk_id: deterministic artifact identity
  - document_id + document_content_sha256: source/version lineage
  - start_char / end_char: exact half-open source span
  - content_sha256: chunk payload fingerprint
  - strategy_id: chunking implementation/config identity
  - metadata: immutable propagated metadata
```

`IngestionPipeline` composes source loading and chunking while returning both source documents and ordered chunk artifacts.

## Shared retrieval contract

Every retriever consumes a `RetrievalQuery` and returns `RetrievalResult` objects.

`RetrievalQuery` contains:

- query text;
- `top_k`;
- an `AccessPrincipal` with optional tenant identity and groups;
- optional chunk IDs to exclude before corpus statistics, scoring, and fusion, for evaluation tasks that place the query document inside the corpus.

`RetrievalResult` contains:

- the original provenance-bearing `Chunk`;
- one-based rank;
- retrieval method;
- raw method-specific score;
- explicit score kind;
- hybrid component contributions when applicable.

Raw cosine and BM25 scores are not assumed to be calibrated. Hybrid retrieval fuses ranks using RRF and retains each component's original rank, score, and score kind as separate metadata.

## Access model

Protected chunks carry namespaced metadata generated by `PermissionPolicy`:

- `atlasrag.access.tenant`;
- `atlasrag.access.groups`, a deterministic comma-separated group list.

The visibility rule is conjunctive:

1. no policy fields means public;
2. a tenant field requires an exact tenant match;
3. a groups field requires membership in at least one allowed group;
4. when both are present, both requirements must pass.

Blank or malformed protected metadata raises during indexing. It never falls back to public visibility.

### Enforcement by path

- Exact dense: filters indexed candidates by policy before query embedding and cosine scoring.
- BM25: filters candidates first, then computes document counts, document frequencies, and average length only over visible chunks.
- Hybrid RRF: requests already-authorized component lists and fuses only those results.

This local baseline proves that unauthorized chunks are not returned. BM25 tests also prove that adding an unauthorized matching document does not change the authorized caller's score.

## Exact dense retrieval

`EmbeddingModel` separates embedding providers from retrieval semantics. `ExactDenseRetriever`:

1. validates one vector per chunk;
2. validates dimensions, finite values, and non-zero vectors;
3. stores the original chunk beside the vector and validated policy;
4. filters by principal;
5. performs exhaustive cosine similarity;
6. sorts by descending score and then chunk ID;
7. returns provenance-bearing results.

Exact search remains the correctness reference. ANN should be added only when a measured corpus scale justifies it, behind an optional dependency, with recall checked against this path on a frozen fixture.

## BM25 lexical retrieval

`BM25Retriever` uses a dependency-light Unicode word-token baseline and the Robertson-style positive IDF form:

```text
log(1 + (N - df + 0.5) / (df + 0.5))
```

It exposes configurable `k1` and `b`, defaults to `1.5` and `0.75`, returns only positive matching candidates, and uses chunk ID for stable ties.

The implementation deliberately recomputes corpus statistics over the visible subset for each query. That is appropriate for a small local correctness and security artifact, but not a claim of scalable production architecture. A production design would likely use policy-partitioned indexes, global statistics, or a search engine with integrated authorization and distributed scoring.

## Reciprocal Rank Fusion

`ReciprocalRankFusionRetriever` indexes the same chunk sequence in BM25 and exact dense retrievers. For each component result at rank `r`, it adds:

```text
1 / (rrf_k + r)
```

The default `rrf_k` is 60. `candidate_k` controls how deeply each component list is searched before fusion. Fused ties use chunk ID for deterministic ordering.

RRF is selected because it combines rankings without pretending BM25 and cosine values share a meaningful numeric scale. The fused score is an RRF score, not a probability or calibrated relevance estimate.

## Identity and provenance decisions

### Separate source identity from source version

`document_id` is deterministic for a normalized source URI. `content_sha256` identifies the exact text payload. A logical source can therefore retain identity while its content version changes.

### Preserve exact chunk lineage

A chunk carries source URI, document ID, document content digest, exact character offsets, chunk digest, strategy ID, and immutable metadata. Retrieval results retain that object directly, avoiding a second provenance lookup.

### Keep chunk identity stable where defensible

Chunk identity includes logical document ID, strategy configuration, character span, and chunk digest, but not the whole-document digest. An unchanged span can retain its ID when unrelated source text changes.

### Keep framework dependencies outside the core

Core domain, ingestion, BM25, access control, exact search, and RRF use the Python standard library. The real MiniLM adapter is optional. This keeps the public API stable while later experiments swap model or index implementations.

## Determinism

The current slice controls nondeterminism through:

- deterministic document and chunk IDs;
- immutable metadata snapshots;
- ordered chunk production;
- deterministic tokenization;
- exact dense search;
- fixed BM25 formula and parameters;
- fixed RRF formula and candidate depth;
- chunk-ID tie-breaking on every path.

Embedding providers may introduce their own nondeterminism. Benchmark runs must record model revision, environment, parameters, corpus checksum, and raw output.

## Failure modes addressed

- invalid chunk size or overlap;
- inconsistent text hashes;
- metadata mutation after object creation;
- provenance loss during chunking or retrieval;
- embedding count, dimension, finite-value, or zero-vector violations;
- duplicate chunk IDs in one index;
- blank queries and invalid `top_k`;
- malformed permission metadata becoming public;
- tenant or group leakage on dense, lexical, or hybrid paths;
- unauthorized BM25 documents perturbing visible statistics;
- non-deterministic equal-score ordering;
- hybrid fusion adding incomparable raw scores.

## Deferred failure modes

- source aliases and moved URIs;
- stale persisted chunks or embeddings after source updates;
- model revision invalidating stored vectors;
- policy changes invalidating indexes;
- ANN recall loss under selective authorization filters;
- partial remote index failures and degraded-mode signaling;
- benchmark leakage into tuning;
- quality improvements that hide latency, memory, or cost regressions;
- context construction or generation that loses citation provenance;
- distributed term statistics and multi-node consistency.
